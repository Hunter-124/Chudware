Originally generated by `tools/cpp_perf_bench.py`. This is the speed counterpart to the parity harnesses (cpp_parity / solver_diff / mate_diff / cpp_eval_parity / cpp_session_parity), which prove the two engines agree numerically. Here we time the **same inputs** through both and report the speedup.

> **Headline:** on heavy in-process **build** work (feature compile + doc rebuild, both incl. tessellation — the path the shipped one-process app takes), the C++ core is **~1.9× faster** than the Python engine on this machine. The constraint **solvers** win far bigger in-process (~10–18×, see the spawn-subtracted notes). A few **tiny ops** (evaluate, single STL export) are actually *slower* in C++ (~0.5–0.6×) because the per-call C-ABI JSON boundary dominates when there's almost no compute to amortise it. Every class — wins and losses — is below.

### Per-class notes

- **3D mate solve** — cpp time includes ~4.6 ms/call process spawn (32 calls); the in-process app pays none of it; spawn-subtracted cpp≈33.1 ms total → ~11.4x
- **Feature compile + tessellate** — compile + tessellate-all-bodies + write .aicm on BOTH engines (matches the doc_compile_cpp RPC; build123d/ocp 7.8.1 vs OCCT 7.9.3); 1 item(s) skipped (one engine failed/unavailable)
- **Doc rebuild + tessellate** — includes tessellation + .aicm write on both engines (the host's per-edit cost); 1 item(s) skipped (one engine failed/unavailable)
- **Evaluate (mass/section/measure)** — body built once; only the evaluate call is timed (OCCT BRepGProp + eigensolve)
- **Tessellate → STL export** — tessellate + STL write on both engines (file-IO cost is paid by both)

## Methodology

- **Warm-up:** each engine path is exercised before timing; the cold first sample (import / JIT / OCCT init) is discarded. Per item: discard 3, then median of 25 samples.
- **Median, not mean** — robust to a scheduler hiccup on a shared box.
- **Only items where BOTH engines succeed are timed**, so a fast error path is never compared against real work. Skipped counts are reported per class.
- **Two C++ paths, clearly separated:**
  - *in-process C-ABI* (`libaicad.dll` via `aicad_call`) — what the shipped single-process app actually calls. This is the fair, headline path: **no process spawn**, no IPC.
  - *CLI spawn* (`sketch_cli` / `mate_cli`) — the fast non-OCCT differential-test binaries. Each call spawns a process, so its wall-clock is dominated by **startup overhead**, not the solve. For these classes we measure the spawn floor (a trivial input) and also report a spawn-subtracted estimate. The real app links the solver in-process, so it pays the subtracted number, not the CLI number.
- **Python is timed in-process** (no spawn) for every class — the Python oracle functions are imported and called directly, so the Python column is its best case.
- **No cherry-picking** — every op class is listed, including any where C++ loses.

## Honest summary

- The **in-process compile / rebuild** classes are the representative ones for real modelling work: they use the exact C-ABI the shipped app calls, do substantial OCCT work, and are where the rewrite's thesis (speed + one process) is actually tested. Read the build speedup off those rows.
- **Where C++ LOSES (evaluate ~0.5×, single STL export ~0.6×):** these are tiny ops (a mass-property integral, one face measure, one box exported). The C++ result is marshalled across the C-ABI as a JSON string and re-parsed in Python on every call; with almost no compute to amortise that boundary, the marshalling *is* the cost. The Python side here is timed as a raw in-process function call with **no** RPC boundary (its absolute best case), so these rows are conservative for C++ and still come out sub-1×. This is the floor cost of the C-ABI on small payloads, **not** a slower geometry kernel — the same ops inside a larger batch (the rebuild class) are 4–5× faster.
- Both engines call into OCCT (the C++ core directly; the Python engine via build123d/ocp). For OCCT-bound work (booleans, fillets, lofts) the heavy lifting is the *same kernel* on both sides, so the speedup there reflects the **Python orchestration / object-marshalling overhead removed**, not a faster geometry kernel. Pure-Python-bound work (the constraint/mate solvers, region finding, selector resolution) is where the C++ rewrite wins biggest.
- The **CLI-measured sketch/mate** rows look unflattering or even slower for C++ *because of process spawn* — that overhead does not exist in the shipped app, which links the solver in-process. The spawn-subtracted estimates in the notes are the representative per-call figures.
