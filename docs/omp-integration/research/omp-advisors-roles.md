## (a) OMP "advisor" — sidecar watcher agent

**Concept**: a background full-agent (own model, own tools, own transcript) that watches the *primary* agent's transcript and injects short `<advisory>` notes. Not a role of the primary — a second concurrent agent process wired into the primary's message stream.

- Config/discovery: `packages/coding-agent/src/advisor/config.ts:20-47` — `AdvisorConfig{name, model?, tools?, instructions?}` loaded from `WATCHDOG.yml`/`WATCHDOG.yaml` search path (`discoverAdvisorConfigs`, tested `config.test.ts:32-56`). Multiple named advisors possible; `sharedInstructions` prepended to all. Tools default to `read/grep/glob`; explicit empty list disables tools; can grant mutating tools (`edit/write/bash`) since "the advisor is a full agent" (`config.ts:14-18`).
- Per-advisor stable provider session id: `getOrCreateAdvisorProviderSessionId` (`config.ts:72-87`), UUIDv7-keyed by `primarySessionId + slug`.
- Runtime/host contract: `advisor/runtime.ts:1-93` — `AdvisorRuntimeHost` interface: `snapshotMessages()`, `enqueueAdvice(note, severity)`, `obfuscator` (redacts primary transcript before sending to advisor model), `maintainContext()` (promotes advisor to bigger sibling model near context limit), `beginAdvisorUpdate()` (resets per-update gate), `onTurnError()` (credential-rotation hook so exhausted accounts don't get re-hit), `notifyFailure()`. Also has `AdvisorOutputQuarantinedError` + prompt-injection hazard regexes (`ADVISOR_OUTPUT_ONLY_HAZARDS`, `runtime.ts:81-92`) that quarantine advisor output containing account-deletion claims, instruction-override attempts, destructive `rm -rf`, etc. — the advisor's own output is treated as untrusted model output, same threat model as a subagent.
- Emission control: `advisor/emission-guard.ts` — `AdvisorEmissionGuard` dedupes near-duplicate/no-op notes ("Stop.", "Done.", "No issue; continue.") via `normalizeAdvisorNote`, FIFO history cap 4096, rate-limits to 1 accepted `advise()` per advisor prompt cycle (`emission-guard.ts:96-133`). Motivated by a real incident (#3520: 309 advise calls / 92 unique notes flooding the primary).
- Tool surface: `advisor/advise-tool.ts:10-64` — `AdviseTool` (schema `{note, severity?: "nit"|"concern"|"blocker"}`), batched into one `<advisory severity="..." advisor="...">note</advisory>` block per note (`formatAdvisorBatchContent`), injected as a `role:"custom", customType:"advisor"` message. The primary's system prompt never mentions advisories — the `<advisory>` tag + `guidance="weigh, don't blindly obey"` attribute is the only framing (`advise-tool.ts:46-50`).
- Delivery/interruption: `resolveAdvisorDeliveryChannel` decides whether a note steers the running turn (interrupts, e.g. for `blocker` severity) or queues passively; `isInterruptingSeverity`, `isAdvisorInterruptImmuneTurnActive` gate this (referenced in `__tests__/advisor.test.ts:17-35`). Steering integrates with the general `agentLoop` pause/interrupt gate at `packages/agent/src/pause.ts:4-6` ("Every agent in a process — main session, in-process subagents, advisor — funnels through agentLoop").
- Transcript persistence: `advisor/transcript-recorder.ts`, filename via `advisorTranscriptFilename`/`isAdvisorTranscriptName` — advisor gets its own `.jsonl` sidecar per session, separate from the primary transcript.
- Trigger cadence: driven per primary-turn update from the host (agent-session integration in `packages/coding-agent/src/session/agent-session.ts`, referenced at `advisor.test.ts` and CHANGELOG entries e.g. "advisor role resolves to a reasoning model... `#resolveAdvisorRuntimeDescriptors`"). Effectively: after each primary model/tool step, host calls `agent.prompt()` on the advisor with the redacted transcript delta; advisor may call `advise()` 0-1 times (rate-limited) per cycle.
- UI: `/advisor on|off|config` slash command; Model Hub inline role assignment strip for `modelRoles.advisor` (CHANGELOG `packages/coding-agent/CHANGELOG.md:516`, `:717`).

## (b) OMP agent ROLE calling — subagent definitions, model routing, dispatch

Not a "role card" system like CAD's — OMP's unit is a **subagent definition** (frontmatter `.md` file), invoked exclusively through the `task` tool; no adopt-role/persona-switch concept on the primary.

- Definition shape: `AgentFrontmatter{name, description, ...}` + markdown `template` (system prompt) — `packages/coding-agent/src/task/agents.ts:20-34`.
- Discovery: `discoverAgents(cwd, home)` — `task/discovery.ts:70` — walks project `.omp/agents/` up the tree, user `~/.omp/agents/`, and OMP extension package `agents/` roots (`listOmpExtensionRoots`, Claude-marketplace-compatible), returns `{agents, projectAgentsDir}`. Memoized per-cwd in `task/index.ts:464-473` (`discoveryMemo`).
- Dispatch entry point: `TaskTool` — `task/index.ts:496-608`. `class TaskTool implements AgentTool<...>`, `name = "task"`, `approval = "exec"`, `static async create(session)` discovers agents at session start.
- Model routing per role: settings `task.agentModelOverrides` (per-agent-name model override) surfaced in the agent dashboard (`modes/components/agent-dashboard.ts:434-435`); `task.disabledAgents` gates which are offered; default agent resolved via `resolveSpawnPolicy(session.getSessionSpawns()).defaultAgent`.
- Spawn param shapes: flat single-spawn `{agent?, task, context?, isolated?}` vs batch `{context, tasks: [{name?, agent?, task, isolated?}, ...]}` gated by `task.batch` setting — validated in `validateShapeParams`/`validateSpawnParams` (`task/index.ts:226-288`).
- Concurrency: session-scoped `Semaphore` sized by `task.maxConcurrency`, resized in place before every acquire so a live settings change applies immediately (`task/index.ts:543-596`); `mapWithConcurrencyLimit` fans out batch spawns bounded by the same semaphore (`task/index.ts:1141-1170`). Background execution optionally routes through `AsyncJobManager` when `async.enabled` (`task/index.ts:11-13, 675-678`).
- Isolation modes: `session.settings.get("task.isolation.mode")` controls whether a subagent gets an isolated worktree/context (`task/index.ts:1211`).
- IRC-style peer messaging between subagents: `isIrcEnabled(settings, taskDepth)` (`task/index.ts:571`) — subagents can message each other/peers, separate mechanism from delegation depth.
- Result handoff: `renderResult`/`renderCall` in `task/render.ts`; `AgentOutputManager` (`task/output-manager.ts`) captures streamed progress; sync path returns merged per-spawn payload (`task/index.ts:343-346`); async path delivers via job settlement.
- No adopt-role/persona-switch primitive on the primary agent itself in OMP — "role" = which agent-definition file is spawned as a *child*, not a live persona swap on the running session.

## (c) OMP delegation / swarm orchestration

Two independent mechanisms, not unified:

1. **`task` tool** (above) — ad hoc single/batch subagent spawn, semaphore-bounded, optional async jobs, no persistent DAG.
2. **`swarm-extension` package** — declarative multi-agent pipeline via YAML, separate CLI extension (`packages/swarm-extension/src/cli.ts`, `extension.ts`).
   - Schema: `packages/swarm-extension/src/swarm/schema.ts:5-158`. `RawSwarmConfig{name, workspace, mode?, target_count?, model?, agents: Record<name, {role, task, extra_context?, reports_to?, waits_for?, model?}>}` parsed via `Bun.YAML.parse` (`parseSwarmYaml`, line 57), normalized to `SwarmDefinition{name, workspace, mode: "pipeline"|"parallel"|"sequential", targetCount, agents: Map<string,SwarmAgent>, agentOrder}`. `validateSwarmDefinition` (`schema.ts:120-157`) checks `waits_for`/`reports_to` reference real agents, no self-reference, `target_count` only valid in pipeline mode.
   - DAG/state: `swarm/dag.ts`, `swarm/state.ts` (`StateTracker` — per-agent status/iteration/log, referenced `executor.ts:18,58-63`), `swarm/pipeline.ts` (sequencing), `swarm/render.ts` (progress UI).
   - Execution: `swarm/executor.ts:41-103` `executeSwarmAgent(agent, index, options)` — wraps OMP's own `runSubprocess` from `@oh-my-pi/pi-coding-agent` (the same subagent infra `task` tool uses), builds an ad hoc `AgentDefinition{name, description, systemPrompt: buildSystemPrompt(agent), source:"project"}` from `role + extra_context`, runs with the task text as user prompt, full tool access, in the swarm workspace dir. State updates via `stateTracker.updateAgent`/`appendLog`.
   - So swarm agents are NOT declared as `.omp/agents/*.md` files — they're synthesized per-YAML-entry and executed through the same subprocess primitive as `task`. No separate model-routing table; `model`/`modelOverride` passed straight through per-agent or swarm-wide.
   - Concurrency model: `mode: parallel|sequential|pipeline` in the YAML controls DAG scheduling in `swarm/pipeline.ts`/`dag.ts` (not separately dumped here — file list confirms responsibility split); no shared semaphore with `task` tool's `task.maxConcurrency` (separate extension, separate settings surface).
3. General agent-loop plumbing that all of the above funnel through: `packages/agent/src/agent-loop.ts` (turn loop, pause/steering at line 2367-2369), `packages/agent/src/pause.ts` (single pause gate shared by main/subagents/advisor).

No org-chart/department/council concept exists anywhere in OMP — no counterpart to CAD's `org.py`/`councils.py`. No approval-chain/budget-meter/depth-cap system either — OMP bounds fan-out only via `task.maxConcurrency` semaphore and (for swarm) YAML DAG shape; no token-budget inheritance, no kill-switch tree, no hard nesting-depth cap enforcement found in OMP task/swarm code (CAD's `delegation.py` has these explicitly: `max_subagent_depth`, `soft_depth_limit`, `max_agents`, `BudgetMeter`, `kill()`).

## (d) Prompt/skill/persona catalog

OMP's closest analogue to a role-card catalog is the `.omp/agents/*.md` frontmatter files discovered by `discoverAgents` (per-project + user + plugin roots), each a name+description+system-prompt template — flat, no schema versioning, no stage vocabulary, no tool-allowlist enforcement point beyond whatever the agent definition's own tool list says. OMP also has a general `skills/`, `hooks/`, `tools/` extension-root discovery mechanism (`discoverAgents` mirrors sibling scanners per CHANGELOG `coding-agent/CHANGELOG.md:747`) but that's a plugin/extension system, not a role/advisor system per se.

## CAD counterparts

- **`services/agent/roles.py`** (1064 lines) — role-card + playbook loader/validator/context-assembler/handoff-validator/GBNF-grammar-emitter. `RoleCard{id, goal, system_prompt, ...}` loaded from `services/agent/roles/*.yaml` (13 authored cards), validated against contract `aicad.role/1`; `Playbook{id, stage, steps, exit_gate}` from `services/agent/playbooks/*.yaml` (`aicad.playbook/1`); `assemble_context()` builds the §9.1-ordered turn context (system prompt → ledger render → stage state → advisory → playbook step → history); `apply_tool_policy()` binds allowlist into MCP `tool_registry` — the ONE enforcement point (unlike OMP where each subagent's own tool list is the boundary, less centrally enforced). `validate_handoff()` + `schema_to_gbnf()` constrain local-model structured output — no OMP equivalent at all (OMP relies on provider-native JSON schema tool-calling, not GBNF grammars for local models).
- **`role_catalog.py`** — `ROLE_BRIEFS` dict (28 roles: model3d, sketch2d, orchestrator, overseer, advisor, department_manager, etc.), `PRIMARY_BUILD_ROLES`, `get_role_adoption_mode()` (`supervised`|`free`). This IS a persona-catalog with adopt/switch semantics OMP entirely lacks.
- **`role_adoption.py`** — `adopt_role()`/`request_role_change` tools: root/main may freely switch its own role card; subagents under `supervised` (default) must request via advisor/main; `delegate(role=...)` to spawn a child with another role is always allowed. No OMP analogue — OMP's primary session never swaps its own persona.
- **`role_models.py`** (1996 lines) — per-role model routing (`ai_roles` config: advisor|task|planning|vision|default|plm|redaction → `{provider, model}` or `"auto"`), thinking-effort per role, ranking-based auto model pick with rankings precedence user>measured>shipped, hard loopback-only refusal for `redaction` role. Roughly analogous to OMP's `modelRoles.advisor` + `task.agentModelOverrides`, but far more structured (ranking system, difficulty-derived thresholds, compliance carve-outs) — nothing in OMP resembles the ranking/auto-pick engine.
- **`delegation.py`** (1054 lines) — `DelegationTree`/`DelegationNode`/`BudgetMeter`/`ApprovalState` — hard nesting cap (`max_subagent_depth`, default 2), soft depth warning (8), max agent count (64) with advisory events, tree-wide token budget inheritance/auto-revoke, human kill-switch revoking the whole tree, approval chain (depth-1 auto, `ponder` kind auto, deeper worker requires overseer/human approval). Far more governance than OMP's task-tool semaphore + swarm YAML DAG — no OMP equivalent to budget inheritance, approval chain, or kill-switch.
- **`councils.py`** (1059 lines) — multi-seat deliberation (same model, different persona system-prompts) producing typed positions round 1, integrate/dissent round 2 with `trigger_condition`; `DissentsRegistry`, policy-driven enable/breadth/diverse-models/temperature (`resolve_policy`). No OMP counterpart whatsoever — OMP's advisor is single-voice, not multi-seat deliberation.
- **`org.py`** (690 lines) — department clustering from a deliverable manifest, channels (auto-created from `depends_on`), mandatory `interface_change` messages gating stage exit, request/resolution with no-silent-expiry guarantee, periodic department reports, overseer concern-aging feed. No OMP counterpart — OMP has no org-chart/department/channel abstraction.
- **`coordination.py`** (488 lines) — per-run shared work board: exclusive claims on doc/feature/file resources across parallel subagents, file-backed with `flock`, conflict (not deadlock) semantics. OMP has no equivalent — parallel `task` spawns share no resource-claim registry; conflicting concurrent edits are only implicitly avoided by agent behavior/isolation mode.
- **`proactive_advisor.py`** (406 lines) — opt-in, deterministic-first, token-cheap mid-run nudge system: cooldown (3 tool calls/45s), fail-streak/same-tool-twice triggers, optional 1-shot LLM call capped at 1/turn, 3/run. Conceptually the closest CAD analogue to OMP's advisor, but architecturally opposite: CAD's is cheap/deterministic-first/opt-in and fires *within* the existing role's turn loop (no second full agent), while OMP's advisor is a full standing sidecar agent with its own model/tools/transcript that runs continuously alongside the primary. CAD has no full-agent watchdog.
- **`subagent_registry.py`** (324 lines) + `subagent_rpc.py` — file-backed cross-process registry (`~/.local/share/Chudware/cache/subagents/<id>.{json,transcript.jsonl,steer.jsonl}`) so the GUI (served by a different process, `engine_oracle/worker.py`) can enumerate/steer running subagents. Steering is append-only, consumed at next turn boundary (`agent_turn.run_turn`), never a hard interrupt. OMP's steering is in-process (`pause.ts` gate) and can genuinely interrupt mid-tool-batch for `blocker`-severity advisor notes — CAD's is strictly cooperative/next-boundary. This is a real architectural gap if CAD's GUI needs live cross-process interrupt (it currently doesn't have it).
- **`council_policy.yaml`** — policy config for `councils.py` (enabled/breadth/diverse_models/temperatures per stage×tier). No OMP counterpart.

## Summary (≤300 words)

OMP's "advisor" is a full standing sidecar agent (own model/tools/transcript) that watches the primary's transcript and injects `<advisory>` notes, with real hardening: an emission-guard that dedupes/rate-limits noisy models (fixed a real 309-note-flood incident, `advisor/emission-guard.ts`), and output-quarantine regexes treating the advisor's own text as untrusted (`advisor/runtime.ts:81-92`). CAD's `proactive_advisor.py` is architecturally lighter — deterministic-first, cooldown/cap-gated, occasional 1-shot LLM call — not a standing agent. OMP's "role" system is just spawnable `.omp/agents/*.md` frontmatter files dispatched via the `task` tool (semaphore-bounded concurrency, batch spawn, async jobs); there's no persona-adoption or role-card schema. CAD's `roles.py`/`role_catalog.py`/`role_models.py`/`role_adoption.py` are considerably more advanced (versioned schema, tool-allowlist enforcement point, GBNF grammar for local models, ranking-based model routing, self-adoption with supervised/free modes) — nothing to port there, only KEEP.

CAD's delegation.py (budget-tree inheritance, approval chain, hard depth cap, kill-switch) is architecturally ahead of OMP's task tool, which only bounds fan-out via a resizable semaphore — KEEP CAD's, don't replace.

The one genuine capability gap is OMP's `swarm-extension`: a declarative YAML DAG (agents with `waits_for`/`reports_to`, pipeline/parallel/sequential modes) — CAD has no equivalent scheduler (org.py clusters departments but doesn't schedule a DAG). Recommend PORTing the schema/DAG concept as a new CAD module executed via CAD's own delegation.py, not bridging to OMP's bun runtime (which depends on `Bun.YAML` and `runSubprocess` internals).

Net: mostly KEEP CAD's governance layers (councils, org, coordination, delegation, role adoption — all OMP-absent or weaker); SIDECAR the advisor engine for its hardened watcher logic; PORT the small emission-guard/quarantine algorithms and the swarm DAG concept; no FORK candidates here — OMP's role/delegation code is thinner than CAD's, not a base to build CAD's UI on.
