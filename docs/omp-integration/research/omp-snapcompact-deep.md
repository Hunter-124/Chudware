# OMP snapcompact deep-dive — data-loss/corruption revamp research

Source: `/home/hunter/Repositories/CAD/scratch/omp-src/packages/snapcompact/src/snapcompact.ts` (1977 lines, read in full), native renderer `crates/pi-natives/src/snapcompact.rs`, compared against CAD `/home/hunter/Repositories/CAD/services/agent/compaction.py` (1054 lines, read in full). No existing porting-docs file on snapcompact specifically (glob for `*snap*` under `omp-inspection/porting-docs` returned nothing — this feature is undocumented there).

## 1. Algorithm end-to-end

### 1.1 Trigger & inputs (`compact()`, snapcompact.ts:1849-1976)
Called by the host agent with a `CompactionPreparation`: `firstKeptEntryId`, `messagesToSummarize`, `turnPrefixMessages`, `tokensBefore`, `previousSummary`, `previousPreserveData`, `fileOps`. Throws if `firstKeptEntryId` is empty (snapcompact.ts:1854-1856) — the caller (agent-core, not in this file) is solely responsible for deciding the keep/discard boundary; snapcompact never re-derives it. **This is unlike CAD, which owns `find_cut_index` itself (compaction.py:462-493).**

### 1.2 Serialization (`serializeConversation`, snapcompact.ts:770-899)
Converts the discarded message window into a dense `¶user:/¶think:/¶ai:/¶call:` transcript:
- Tool results flagged `useless===true && !isError` are dropped entirely, including their originating call (snapcompact.ts:797-799, 851).
- Every tool-result body is truncated head/tail (`TOOL_RESULT_MAX_CHARS=2000`, 60%/40% split) via `truncateForSummary` (snapcompact.ts:706-717, 741-749, 811). Wrapped in `<out>…</out>`, body dimmed with `DIM_ON/DIM_OFF` (zero-width ink toggles) so archived tool noise reads quieter than conversation (rendering-time only, not data loss).
- Tool-call args: each arg value capped at `TOOL_ARG_MAX_CHARS=500`, and the whole arg list capped again at `TOOL_CALL_MAX_CHARS=2000` (snapcompact.ts:863-873) — i.e. up to two nested lossy truncations for a single write/edit call whose body is inline in args.
- CAD mirrors these three caps almost exactly: `TOOL_RESULT_MAX_CHARS=2000`, `TOOL_ARG_MAX_CHARS=500`, `TOOL_CALL_MAX_CHARS=2000`, `TRUNCATE_HEAD_RATIO=0.6` (compaction.py:28-31), same head/tail elision shape (`truncate_middle`, compaction.py:80-92). This is clearly a ported/aligned design already.

### 1.3 Normalization for rendering (snapcompact.ts:917-1195)
`normalize()`/`normalizeWithStats()` (used only by OMP, CAD text-phase has no analogue) prepares text for pixel-font rendering:
- ANSI stripped, whitespace collapsed, newlines become a solid-block glyph `NEWLINE_GLYPH` (U+2588) (snapcompact.ts:980, 1090).
- Curly quotes/dashes/bullets/arrows folded to ASCII via `CHAR_FOLD` table (snapcompact.ts:924-975).
- Status emoji folded to bracket tokens (`✅→[OK]` etc, snapcompact.ts:1004-1027); all *other* pictographs are **silently dropped** (not even a `?`) — snapcompact.ts:1163 (`else if (EMOJI_PICTOGRAPH.test(ch)) {}` — no-op, character vanishes).
- Any other unrepresentable glyph (no font coverage, no ASCII fold) prints as literal `?` and increments `fallbackCount` (snapcompact.ts:1164-1168).
- `scanRenderability()` computes `fallbackCount/totalGraphics`; "safe" threshold is ≤5% (snapcompact.ts:1188-1195). Used only to pick between the default shape and the Silver CJK fallback font (`resolveShapeForText`, snapcompact.ts:411-421) — **it does not gate whether rendering proceeds**; even an unsafe (>5% `?`) text is still rendered, just without trying Silver.

### 1.4 Shape/model selection (snapcompact.ts:204-421)
Picks a `Shape` (font/cell/frameSize/billing) by provider family (Anthropic/Google/OpenAI) and model-id regex table (`MODEL_VARIANTS`, snapcompact.ts:338-356), with per-family frame-size/token-billing formulas (snapcompact.ts:234-247). This entire subsystem — and thus the "PNG-frame path requires a vision model" property — has **no CAD counterpart**; CAD's compaction.py explicitly defers this ("frames reserved for vision phase", compaction.py:33,609,668).

### 1.5 Archive layout / foveation (`planArchive`, snapcompact.ts:1750-1834)
Core compaction decision of what's kept verbatim as text vs. rendered as an image vs. dropped:
1. One HQ-frame-capacity of text is kept **verbatim** at the oldest edge (`textHead`) and one at the newest edge (`textTail`) — `TEXT_EDGE_PAGES=1` (snapcompact.ts:757, 1752).
2. Everything between the edges (`imageText`) is candidate for imaging.
3. If `imageText` fits within `maxFrames` HQ pages, all of it is imaged, **zero truncation** (snapcompact.ts:1799-1806).
4. If it overflows `maxFrames`, foveation kicks in: HQ frames at both ends of the imaged middle (`HQ_EDGE_FRAMES=3` each), a denser Low-Quality companion shape (`denseCompanion`, snapcompact.ts:1714-1719, ~40% more chars/frame at the identical byte/token bill) for the "least important" center, and if even that center still overflows the remaining frame budget, **the oldest slice of the LQ center is permanently dropped** (`truncatedChars`, snapcompact.ts:1819-1826) — this is the one place inside `planArchive` where source characters are unrecoverably discarded rather than merely re-encoded.
5. Doc-column (CJK newspaper) layout has a *cruder* fallback: no foveation tiers at all — if wrapped pages exceed `maxFrames`, it simply drops the whole *middle* span of pages (keeps 1 oldest + `maxFrames-1` newest), a much larger and less graceful loss (snapcompact.ts:1781-1785).

### 1.6 Frame rendering (native path)
`render()`/`renderMany()` (snapcompact.ts:1451-1531) call `renderSnapcompactPng` from `@oh-my-pi/pi-natives` (Rust, `crates/pi-natives/src/snapcompact.rs`) — a native N-API binary that rasterizes bitmap/TrueType fonts to indexed or RGB PNG and base64-encodes it (confirmed via grep: `render_snapcompact_png` returns `Result<Latin1String>`, size validated against `MAX_FRAME_SIZE`, snapcompact.rs:1197-1208; overflow-input fuzz test asserts no panic, snapcompact.rs:1363-1364). **This native binary is a hard dependency**: no source exists in this package for a pure-JS/Python PNG fallback. If the native module fails to load (wrong platform triple, missing prebuild) `compact()` throws — there's no text-only degrade path *inside this file*.

### 1.7 Where a vision model is required
Once frames exist, they're attached to the LLM request as `ImageContent` blocks (`images()`, `historyBlocks()`, snapcompact.ts:1655-1704) mixed with the two verbatim text edges. **A non-vision model reading this history sees only the text edges + a literal notice string** ("imaged middle above/below", "middle history omitted above") with the actual pixel content invisible to it — text-only models silently lose the entire foveated middle with no textual substitute. There is no code path that renders frames back to text for non-vision consumption; `archiveSourceText()` (snapcompact.ts:1584-1591) only reconstructs `textHead+textTail`, explicitly excluding image content — used solely to feed the *next* compaction pass's shape probe/re-render, not as an LLM-facing fallback.

## 3. Existing safeguards & their gaps

- **Round-trip via `Archive.text`** (snapcompact.ts:541-543, `persistedText` at 1954-1957): every compaction keeps the *full* kept source text (head+imaged-middle+tail, whatever survived foveation) in `preserveData[PRESERVE_KEY].text`, re-folded into the *next* compaction's input (snapcompact.ts:1890-1892, "unfolds the prior archive's source text and treats it as one coherent transcript"). This means frames are **always re-derived from `text`**, never the sole source of truth — a real strength: if the vision model path fails, `archiveSourceText()` can still hand `textHead+textTail` (not the middle) to a summarizer. Gap: once `truncatedChars` chars are dropped from `text` itself (#6/#7 above), that safety net is gone — there is no separate "cold" archive of anything beyond what's kept in `Archive.text`.
- **`firstKeptEntryId`** (CompactionPreparation/CompactionResult, snapcompact.ts:599, 616): the caller's session log presumably still has the raw messages before this ID (this file doesn't delete them — that's the host agent's job, out of scope here) so in principle raw recovery is possible *outside* snapcompact if the host retains full session history on disk. This dossier can't confirm host retention semantics from this file alone — worth checking agent-core's session store.
- **`getPreservedArchive` validation** (snapcompact.ts:1538-1568): defensively filters malformed frame objects (missing `data`/`mimeType`/`cols`/`rows`/`chars`) out of a loaded archive rather than crashing — a soft integrity check, but it only checks *shape*, not that `data` decodes to a valid PNG or matches `cols`/`rows`/`chars`. No checksum/hash field exists in `Frame` at all (snapcompact.ts:509-529).
- **`stripPreservedArchive` / `stripOpenAiRemoteCompactionPreserveData`** (snapcompact.ts:1570-1581, 905-915): clean state-machine hygiene preventing stale archives from leaking forward — good practice, no gap noted.
- **`reinject`**: OMP has no single function named `reinject`; the equivalent behavior is `historyBlocks()` (snapcompact.ts:1667-1704) called at every context rebuild (per the file's own top comment, lines 43-44: "Frames persist in preserveData and are re-attached to the compaction summary message on every context rebuild") — i.e. re-injection is implicit/automatic, not an explicit reversible-action API the way CAD's `reinject_archive()` is a standalone function. This makes OMP's reinjection harder to unit-test in isolation (it's threaded through the live-session rebuild path, not exposed as this dossier's read scope covers) — worth flagging as a portability/testability risk for a Python port.
- No corruption safeguard (checksums, magic byte validation) anywhere in this file for `Frame.data`.
- No hard cap violation alarms: `maxFramesForDataBudget()` (snapcompact.ts:465-467) and `providerImageBudget()` (496-499) both compute soft ceilings but nothing logs/errors when frames are actually dropped at these boundaries beyond the user-facing text notice — no telemetry/metric hook visible in this file.

## 4. Concrete revamp opportunities

1. **Reversibility of foveation drops (fixes risk #6/#7, the biggest gap).** Currently `truncatedChars` in `planArchive` throws source characters away with only a character *count* kept, no recoverable payload. Revamp: persist the dropped middle slice(s) to a side channel (e.g. a `preserveData` sibling key or an on-disk artifact keyed by session+compaction-id) instead of `String` deletion, so a later "expand this archived middle" tool call (or a bigger-context model on a later turn) can pull it back. This mirrors CAD's own `artifact://` recovery pattern already used by `shake_messages`'s placeholder text (`compaction.py:799-802`, `_placeholder()` embeds `artifact://{artifact_id}`) — CAD already solved this for its shake phase; OMP's foveation-drop path has no equivalent and should adopt the same idea.
2. **Archive integrity: add a checksum to `Frame`.** Add e.g. a `sha256` (or cheap crc32) of `data` computed at render time and re-verified at `getPreservedArchive()` load time; treat mismatch as a corrupt/discard-and-refallback-to-text signal rather than silently forwarding a broken PNG to the provider. Low cost (one hash per frame, ~80 frames max).
3. **Cap review — the two hardest caps are highest risk:** `MAX_FRAMES_DEFAULT=80` (line 438, cannot be raised by caller, line 1876) and `TOOL_RESULT_MAX_CHARS/TOOL_ARG_MAX_CHARS/TOOL_CALL_MAX_CHARS` (2000/500/2000). The frame cap directly causes irrecoverable loss (#6) once exceeded — consider either (a) making the ceiling adaptive to the *actual* per-request image budget of the specific model/provider in play (already computed elsewhere as `providerImageBudget`) rather than a single global constant, or (b) implementing opportunity #1 so hitting the cap degrades to "recoverable" instead of "gone."
4. **Text-fallback when no vision model / no native binary.** Two independent failure modes converge on the same fix: (a) a text-only model receiving frame-containing history sees nothing of the imaged middle (section 1.7); (b) if `renderSnapcompactPng`'s native module is unavailable (platform mismatch, sidecar not built) `compact()` currently has no fallback and would throw. Revamp: add a "text-render" mode that emits the exact same `serializeConversation`+`normalize()` transcript as **plain wrapped text pages** (reusing `paginateCells`/`docPages` geometry, just skip the PNG step and emit `TextContent` blocks) whenever (a) the resolved model has no known vision capability, or (b) the native renderer throws/is absent. This is materially most of what CAD's compaction.py *already is* (a permanent text-only mode, `compaction.py:1-14,33` "frames deferred to a future vision phase") — i.e. CAD's whole compaction module can literally serve as this fallback's reference implementation, or even be reused directly as the text tier via the sidecar.
5. **Corruption safeguard for the sidecar/IPC boundary specifically** (relevant to the planned bun-bridge architecture): since Chudware will call `renderSnapcompactPng` across a process boundary (bun sidecar) rather than in-process N-API, add response-envelope validation (length-prefixed framing + the checksum from #2) so a truncated IPC message is *detected* rather than silently persisted as a broken `Frame.data`.

## Summary of biggest findings

The foveation/image path (`planArchive`, snapcompact.ts:1750-1834) is where OMP diverges most sharply from CAD and is also the single biggest data-loss surface: past an 80-frame ceiling (`MAX_FRAMES_DEFAULT`, hardcoded, cannot be raised by callers), it permanently deletes the oldest slice of the dense "low quality" middle tier with only a character count (`truncatedChars`) surviving — no recoverable payload, unlike CAD's `shake_messages()` which always leaves an `artifact://`-recoverable placeholder. The doc/CJK layout path is cruder still, dropping whole page spans with no foveation tiers at all. A hard native-binary dependency (`renderSnapcompactPng` in Rust via `@oh-my-pi/pi-natives`) means any bun-sidecar port inherits both a vision-model requirement (non-vision models see zero content for the imaged middle — no textual fallback exists in this file) and a new IPC-corruption surface, since `Frame.data` carries no checksum and is never validated after generation or after reload. Text-truncation caps (tool result/arg/call, 2000/500/2000 chars) are already essentially identical between OMP and CAD — this part is safe to keep as-is. CAD is meaningfully ahead of OMP in three concrete ways worth porting back: (1) `apply_supersede_reads` — dedupes repeated file reads before archiving, reducing pressure on OMP's foveation cap in the first place; (2) `shake_messages`'s recoverable-placeholder pattern, directly transferable to fix OMP's unrecoverable foveation/doc-layout drops; (3) an explicit standalone `reinject_archive()` pure function vs. OMP's implicit rebuild-time weaving, better for testability and for a clean fork/port. Recommended revamp priorities: (1) make foveation drops recoverable via an artifact-style side channel (reuse CAD's pattern), (2) add per-frame checksums validated on load and after any IPC hop, (3) build a text-only rendering fallback for non-vision models / missing native binary — for which CAD's compaction.py can literally serve as the reference (or even be reused as) that fallback tier, given how close the two truncation policies already are.
