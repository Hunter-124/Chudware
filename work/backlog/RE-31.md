## Context
`services/mcp/test_reveng_tools.py` (and `test_mcp_freshness.py`) install a `_FakeFastMCP`
stub into `sys.modules["mcp"]` (or the `mcp.server.fastmcp` path) at import/module scope and
do NOT restore it. This leaks to sibling test modules run later in the same pytest session:
`services/mcp/test_reveng_e2e_datasheet.py::test_reveng_session_ingest_via_mcp` then does
`from mcp.server.fastmcp import FastMCP` and gets the fake (no `_tool_manager`), failing with
`AttributeError`. Each test PASSES in isolation; the failure is ordering-dependent. RE-17
independently hit the same real-first-stubbing hazard in services/dag tests.

## Write-set
- `services/mcp/test_reveng_tools.py` and/or `services/mcp/test_mcp_freshness.py` — install the
  fake via a fixture / setUp+tearDown (or `unittest.mock.patch.dict(sys.modules, ...)`) that
  RESTORES the real `mcp` module after the test class/module, so no global leak.
- Optionally `services/mcp/test_reveng_e2e_datasheet.py` — make its FastMCP import resilient.

## Acceptance
- `python3 -m pytest services/mcp/test_reveng_tools.py services/mcp/test_reveng_e2e_datasheet.py services/mcp/test_mcp_freshness.py -q` passes with NO ordering-dependent failure (the combined run is currently RED: `_FakeFastMCP object has no attribute _tool_manager`).
- No test assertions weakened; the fake-stub tests still verify what they did before.
