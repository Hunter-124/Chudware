## Context
`services/mcp/test_reveng_research_ingest.py::TestResearchAndIngest::test_url_mode_pdf` PASSES in
isolation but FAILS when run after `test_reveng_make_part.py` or `test_reveng_e2e_datasheet.py`
(combined RE suite is RED, order-dependent). Symptom: `research_and_ingest(url=...)` returns
`{ok:false, reason:"no_data_found"}` instead of the mocked PDF result.

Root cause (diagnosed): `engine_oracle/vision/research_ingest.py`'s `research_and_ingest` resolves
the research/browser fetch functions via a FUNCTION-LOCAL lazy `import` (optional-import pattern).
The test monkeypatches the fetch symbols on the `research_ingest` MODULE (`ri.*`). When no prior
test has imported `services.mcp.research_tools`, the lazy import fails and the code falls back to
the module attribute (which is monkeypatched) → test passes. But once make_part/e2e_datasheet have
pulled `research_tools` into `sys.modules`, the lazy import SUCCEEDS and calls the REAL
(network-less) fetch, bypassing the monkeypatch → `no_data_found`.

## Write-set
- `engine_oracle/vision/research_ingest.py` — resolve the fetch functions through stable
  MODULE-LEVEL references (bound once at import, overridable) so a `monkeypatch.setattr(ri, ...)`
  is always honored, regardless of whether `research_tools` is already in `sys.modules`. Preserve
  the graceful optional-import / offline degradation behavior.
- `services/mcp/test_reveng_research_ingest.py` — only if the correct patch target legitimately
  changes; do NOT weaken assertions.

## Acceptance
- `python3 -m pytest services/mcp/test_reveng_make_part.py services/mcp/test_reveng_e2e_datasheet.py services/mcp/test_reveng_research_ingest.py services/mcp/test_reveng_tools.py -q` passes GREEN (run twice with different module order to confirm no ordering dependence).
- Offline/tools-absent degradation of `research_and_ingest` unchanged (still returns the honest envelope when the real tools genuinely aren't importable).
