# T-F14 — open questions

## Q1 — `render_document` native SVG path has no permissive in-process rasterizer in the §7 engine set

**Context.** Contract §5.4 lists `svg` as a **native path (no subprocess), in-process
rasterize/pass**. But the frozen §7 engine table has no permissive in-process SVG rasterizer:
pypdfium2/pillow/matplotlib cannot rasterize an arbitrary SVG, and adding a new engine (e.g.
cairosvg/resvg) requires a §7 + `contracts/licenses.md` row — outside this task's dep budget.

**What I did (non-blocking).** Implemented `svg_to_pngs` best-effort: use `cairosvg` *iff* it is
already importable in the environment (not a declared dep), else fall back to the LibreOffice
office path, else degrade to `{ok:false, reason:"converter_missing"}`. All other native paths
(pdf/png/csv/md) are fully in-process as specified. SVG previews therefore degrade cleanly and CI
stays green; only SVG-specific preview fidelity is deferred.

**Recommended answer (for integrator sign-off, `deliverables/1`-compatible):** accept the
best-effort SVG behavior as-is for `deliverables/1` — SVG is not one of the `make_*` output
formats and no smoke artifact is an SVG. If native SVG preview is wanted later, add **resvg**
(MPL-2.0) or **cairosvg** (LGPL) as an explicit §7 in-process row in a follow-up (compatible,
non-versioning change). No contract wording change needed now; this is a dep-table gap, not a
seam change.

Status: proceeding on the recommended answer; unblocked work continued.
