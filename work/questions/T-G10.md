# T-G10 Decisions & Questions

## Decision 1: Appdata migration approach (RATIFIED)

**Question:** Should `appdata_root()` move `~/.local/share/AI-CAD` to `~/.local/share/ShopCraft`
on first run, or use an alias/read-both approach?

**Recommended answer (ADOPTED):** Alias / read-both approach — no destructive migration.

**Rationale:** `~/.local/share/AI-CAD/mcp-venv/bin/python` is the interpreter behind the live
MCP server and is referenced by absolute path in pyvenv.cfg and script shebangs. Moving the
directory would destroy the venv (venvs don't relocate), break the running MCP server, and
disconnect every in-flight agent. Copying also produces a dead venv. Recreating the venv
in the new location is an installer concern (setup_mcp_clients.py --setup-venv), not a
startup hook.

**Implementation:** `appdata_root()` returns `~/.local/share/ShopCraft` (new canonical),
but `appdata_root_legacy()` returns the old `AI-CAD` path. Every READ path (finding existing
data) checks legacy if new dir doesn't exist. Every WRITE path creates in the new dir.
`paths.py` exports a `DATA_ROOTS` list to make this available for callers that scan for data.

## Decision 2: Env var rollout scope

**Question:** Do SET sites (gate.sh exports, test setdefault calls) need updating?

**Recommended answer (ADOPTED):** No — SET sites are left as-is in this PR. The dual-read
helper in core_bridge.py and the host binary (AI_CAD_SHOT) makes old names continue to work.
New documentation points to `SHOPCRAFT_*` names. Churning SET sites risks breaking the T-G9
parity harness regression net.

**Note on AI_CAD_SHOT:** This is read by the C++ host binary (ui/imgui) and by the gate.sh
script. For this PR, we add SHOPCRAFT_SHOT as an alias read in the binary's launch wrapper
(gate.sh stage 5) and document the new name. The C++ binary itself is not changed in this PR
(requires rebuild, handled as a follow-up).

---

## Decision 3: Build targets

**Question:** Does the binary need to produce `ShopCraft` in addition to `AI-CAD2`?

**Recommended answer (ADOPTED):** Additive. The CMakeLists.txt adds a post-build symlink
`ShopCraft` → `AI-CAD2` in the output bin/ directory. The existing target name and OUTPUT_NAME
stay as-is so no script breaks. `tools/gui_parity/common.py` continues to find `AI-CAD2`.

---

## Decision 4: MCP server id

**Question:** Should `SERVER_NAME` change from `ai-cad` to `shopcraft` immediately?

**Recommended answer (ADOPTED):** Dual-write approach. `setup_mcp_clients.py` writes the
new `shopcraft` entry AND leaves any existing `ai-cad` entry in place (no delete).
`SERVER_NAME` becomes `shopcraft` for new registrations. The human is instructed to run
`python3 services/installer/setup_mcp_clients.py` to register the new id; old tooling
using `ai-cad` keeps working until they re-register.

---

## Decision 5 (refinement of D1): active_root() picks ONE root, no split-brain

While implementing D1 it became clear that read-fallback-per-file (find_config-style)
risks split-brain: reads from legacy, writes to new, then new shadows legacy with
partial data. Adopted rule instead — `active_root()`: if the ShopCraft dir does not
exist and the legacy AI-CAD dir does, use the legacy dir WHOLESALE (reads + writes);
fresh installs use ShopCraft. Mirrored identically in C++ (platform/paths_linux.cpp,
platform/paths_win32.cpp, core/agent/paths.cpp, services/worker/bootstrap.cpp) so all
processes on a machine agree on one root. Existing machines: zero behavior change.

## Bug found & fixed in passing (in scope — task lists the handoff path)

ui/imgui/src/ui/feature_tree.cpp pollAiCadHandoff() watched
`appdataRoot() + "/AI-CAD/handoff/live.json"` — a doubled path (appdataRoot already
includes the app dir); the host-era code used appdataDir() (the parent). The live
viewport handoff could never fire in the new GUI. Also `_handoff_dir()` in
services/mcp/cad_tools.py fell back to /tmp on Linux (no APPDATA) while the GUI reads
XDG — publisher and reader now both use the alias-aware app root.
