# T-G13 — root cause + fix plan for issue #7 (scenario deadlock)

## Empirical characterization (driver opus-sky, all runs offscreen via `xvfb-run`)

Build: `cmake --preset linux-app && cmake --build build/linux-app`. Backend:
`CHUDWARE_LIBCHUDWARE=<repo>/core/build-occt-linux/bin/libchudware.so`. Worker present ⇔
`CHUDWARE_PYTHON=/usr/bin/python3` set (system python3 has the engine deps on this box).

**Battery, worker PRESENT (20/22 PASS):** all one-shots + m1/sketch/multidoc/fea/flow/
drawing/evalmass/activity/asm PASS with REAL geometry (verified m1.png = filleted+shelled
box, "Engine live (WorkerClient, rev 3)"). Only **cam** (HANG, no PNG) and **glassperf**
(slow: 175 ms/frame × 400 ≈ 70 s > 40 s timeout) fail.

**Battery, worker ABSENT (default box, no venv):** all 10 step machines HANG (124, no PNG);
one-shots PASS but render empty chrome (no worker → no part).

## Root cause — the issue's "mid-loop newPart deadlock" hypothesis is WRONG

`DocMirror::newPart(worker)` returns fine (tree/sketch complete in ~3 s with the worker up).
The hang is entirely in the **shot-capture control flow** (`main.cpp` loop + `scenarios.cpp`
`endFrame`/`captureFrameBudget`), two independent defects:

- **Defect 1 (9 scenarios: m1/sketch/asm/fea/flow/drawing/evalmass/activity/multidoc).**
  Each gates its step-machine body on `st.workerStarted` and only Breaks (in `endFrame`) once
  `xShotDone` is set. `captureFrameBudget()` returns **999999** for every `isScenarioMode()`
  scenario, so the generic frame-budget capture in `main.cpp` never fires for them. When the
  Python worker isn't provisioned (`workerStarted==false`, the default on an unprovisioned
  Linux box), the body never runs → `xShotDone` never set → `endFrame` returns `Continue`
  forever → infinite spin (exit 124, no PNG). This is the dominant, filed hang.
  opua-gale saw it because their step-machine invocations ran without a live worker (or the
  outer `timeout 45/90` was shorter than per-process worker cold-start); `newPart` was never
  the culprit.

- **Defect 2 (cam).** `cam` is in `isScenarioMode()` (budget 999999) but has **no `wantCam`
  branch in `endFrame()`**, so it returns `None` and relies on the generic budget path — which
  is 999999. cam completes its work (`cam-shot: ok=1`) but can NEVER write a PNG, even worker-
  present at 180 s. Structural, not slow.

- glassperf: not a step machine, just slow offscreen (glass blur + profiler). Needs a longer
  timeout, no code fix. Out of the issue's 10.

## Fix (harness-only, within the runner/worker seam; scenarios NOT redesigned)

- **A — `main.cpp` watchdog frame cap.** When `cfg.frame` exceeds a bounded ceiling, force
  `capturePNG + break` regardless of `FrameAction` (incl. `Continue`). Guarantees every
  scenario terminates with a PNG. A between-frames watchdog suffices because in every observed
  hang frames keep flowing (worker-absent spin; cam's post-work spin) — no infinite in-tick
  block exists (all `w.call()` have a 120 s timeout; cam_program returns). This is exactly
  what issue #7 endorses ("hard frame cap / watchdog").
- **B — `endFrame` `wantCam` branch.** Capture + break once `camShotDone` (mirrors fea/flow),
  so cam captures promptly instead of only via the late watchdog.
- **Real captures need the worker provisioned.** The watchdog prevents hangs but a worker-
  absent box captures empty chrome. G8/G9 / Erik's walkthrough need REAL screenshots ⇒ the
  capture path must run with the worker up (`CHUDWARE_PYTHON` / a provisioned venv). Verification
  runs the full battery worker-present and confirms real geometry.

## Question for advisor (Fable)

Fix A+B are clearly in-scope and provably fix the hang. Open question: should T-G13 also make
the **shot harness auto-start the worker** when the venv is absent (fall back to a PATH
`python3` in `worker_client.cpp::start()`, shot-mode only), so real captures are the default on
any box with python3 + engine deps — or leave worker provisioning to the environment/gate and
only ship the A+B harness robustness? My lean: ship A+B now (unblocks by removing the hang),
and add the shot-mode python3 fallback too since it's low-risk here and directly enables real
G8/G9 captures, guarded to shot mode + POSIX. Advisor's call on the fallback's scope.

## ANSWER (Fable)

Ship A+B only — MERGED. The shot-mode python3 fallback is DECLINED for now: implicit
interpreter discovery is exactly the class of env-guessing that produced the T-F8
all-skip trap (tests silently running against a different python than production).
Real G8/G9/G12 captures must run with the provisioned worker EXPLICITLY
(CHUDWARE_PYTHON=<mcp-venv python>) — the G8/G9 task files' verify commands should say
so; a missing worker should stay loudly chrome-only, never silently "work". If G8/G9
find this friction is real in practice, re-raise with evidence and we'll revisit.
