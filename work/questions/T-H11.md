## Q1 — Fix-preview card placement (copilot vs standalone)

**Question.** The DoD says "on rebuild failure the copilot offers diagnosis + fix preview;
apply/reject logged as artifact actions with verifier scores." The driver notes say the copilot
panel is T-F17 / T-G7 territory and, if contested, to go standalone-first per the T-F16
precedent + post a question file. Board check at claim: **T-F17 (Mission-control UX, copilot
action stream) and T-G7 (core-panels migration) are both `todo`/unassigned** — so the copilot
panel (`ui/imgui/src/ui/agent_panel.cpp`, a declared hot-spot) is contested and unowned.

**Recommended answer (implemented).** Ship the fix-preview as a **registered, callable backend
surface** (the true T-F16 analog — T-F16 registered its `render_document`/`list_artifacts`
worker RPCs and deferred only the GUI binding) and do NOT edit `agent_panel.cpp`:
- `services/agent/regen_diagnosis.py` — `diagnose()` produces the diagnosis + editable doc-ops,
  logged as an IP-18 `ai_artifact` correction trace via T-H7's LoggingProvider.
- `services/agent/regen_card.py` — `build_fix_preview()` (diagnosis + editable ops + plain-English
  change list + T-H2 `doc_diff` enrichment + verifier verdict), `emit_action()` /
  `resolve()` (accept/edit/reject → `ai_artifact_action`, correlated to the diagnosis
  `artifact_id`, carrying the verifier score).
- **`services/mcp/regen_tools.py` — the `regen_diagnose` MCP tool (registered append-only in
  server.py)**: the shared, callable backend seam both the copilot and the orchestrator invoke on
  a rebuild-failure event → diagnose + verify (rebuild/compare_parts when the core is present) +
  return the card, logged at IP-18. It is a live surface the moment any caller invokes it.
- T-F17 (or whoever claims the copilot panel) binds the copilot UI to this surface (render the
  card, route the click to `regen_card.resolve` / re-call the tool). Exactly the T-F16 pattern.

**Honesty caveat (stated, not papered over):** the seam is *registered but uncalled* until T-F17
wires it to the rebuild-failure event — so it harvests ZERO real correction traces until then
(the same posture T-F16 shipped its pane in). The plumbing (diagnose→verify→card→IP-18 log) is
proven end-to-end with a mock provider (`services/mcp/test_regen_tools.py`).

**Alternatives considered.** (a) Claim the agent_panel hot-spot and add the card in C++ now —
rejected: contested/unowned panel, high GUI risk, violates the first-claimer/standalone-first
rule. (b) Inline the card into the loop's IP-1 path — rejected: IP-18 is a distinct insertion
point with its own logged artifact; coupling them muddies the correction-trace provenance.

**Ask of the foreman:** confirm T-F17 owns the GUI binding to `regen_card` (seam noted in that
module's docstring), and that a standalone surface satisfies DoD item 1 for this task as it did
for T-F16.
