## Q1 — Does the assembly/user manual (step 5) need the reserved `make_manual` TOOL, or does it
ship as a template under the existing `make_report`?

**Context.** Contract `deliverables/1` §1 names `make_manual` but explicitly **reserves** it:
"it is named here so the tool family and registry `kind` enum have a slot for it, but it is
**not specified** by `deliverables/1`. Do not implement it under this contract." Task T-F15 step
5 asks for "assembly instructions + user manual (md→pdf)". So: is a manual a distinct tool seam,
or just another spec-driven report?

**What I did (non-blocking).** Shipped `assembly_manual` as a **`make_report` template**
(`kind: "report"`, formats docx/pdf), registered against the same generic template registry as
the other four engineering templates. It has `title` / `section` (user-manual prose) / `step`
(exploded/step render image + instruction body + load-bearing torque/fastener_count/gap/preload
callouts) block types. Every load-bearing callout resolves from an attached tool result exactly
like every other template; the render images embed best-effort (missing file → caption, never an
error). `make_manual` remains **reserved and unimplemented**, so `deliverables/1` is unchanged
and the `kind` enum slot is preserved for a future need.

**Recommended answer (integrator sign-off, `deliverables/1`-compatible):** **Accept manuals as a
`make_report` template — do NOT implement `make_manual` for T-F15.** Rationale: a manual is
structurally the same seam as a report (an outline of prose blocks + provenance slots + embedded
renders → a paginated docx/pdf). It needs no new envelope, no new record `kind`, no new error
codes — so a separate tool would be redundant surface a 4B model must learn. Reserve `make_manual`
for a *genuinely different* future shape (e.g. an interactive/structured technical-manual builder
with cross-referenced part numbers, revision control, or multi-document manual sets) — that would
be a `deliverables/2` addition with its own record `kind:"manual"`. Nothing in T-F15's scope needs
that. **No contract change required now.**

**The "md→pdf" note in the step.** The step text says "md→pdf" (implying a markdown→pandoc path).
We render docx/pdf **directly** via the in-process engines already in §7 (python-docx / reportlab)
— no markdown intermediate, no pandoc dependency, CI-green without subprocess converters. The
"md→pdf" phrasing is the *conceptual* pipeline, not a required implementation; direct rendering is
strictly better (fewer deps, provenance enforced structurally rather than in free markdown text).

Status: proceeding on the recommended answer; all five templates land and are green. If the
supervisor wants `make_manual` implemented as a distinct tool, that is an additive follow-up and
does not block T-F15.
