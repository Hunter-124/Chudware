## Context

Pillar 20 Part II (docs/ADVISOR_ARCHITECTURE.md §2.11, contracts/advisor.md §11 —
FROZEN). Hunter directive: an overseer model must catch errors in the workflow/
chain-of-thought/plan and route user-requested fixes/changes so they land correctly.
Trigger-driven (never per-turn): plan ratification, stage exits, failure-card
escalations, preflight overrides, every user change-request. Verdicts return as
advisories (source llm, marked as review findings); repeat blockers escalate to
human. Change-requests get mapped onto ledger + build graph into a scoped change
plan before any mutation.

## Files / areas touched

- `services/agent/advisor/overseer.py` — trigger subscription, context assembly

  verdict parsing/validation, dispatch

- tests: `services/agent/advisor/test_overseer.py`

## Steps

1. Read docs §2.11, contract §11 §12 (routing: overseer binds to `strongest` source
   — hardcode a provider preference list until T-W14 lands, seam it cleanly).
2. Trigger plumbing on the advisory engine (T-W5): subscribe to stage-exit,
   escalation, preflight_overridden events; debounce (one audit per trigger point).
3. Context assembly is BUDGETED (frontier default, but must degrade by tier):
   ledger_render + active buildgraph slice + last N handoffs + advisory/audit
   history fingerprints. Never raw chat logs of workers — handoffs and ledger are
   the audit surface (this is what makes CoT auditing feasible: roles must surface
   reasoning summaries in handoffs, per T-W7 schema).
4. Overseer prompt (in the role card): senior engineering reviewer identity; audit
   ONLY against evidence provided; verdict classes with definitions + one worked
   example each; output = strict aicad.audit/1 JSON; "if the plan is fine say ok —
   invented findings are worse than none."
5. Verdict handling: validate, ledger event, convert to advisory items for the
   working role; blocker-fingerprint repeat counter → ask_user with evidence.
6. change_request(): classify scope from ledger (requirements/dimensions/features/
   parts touched, with refs), draft change plan (ordered edits + checks to re-run),
   audit it (self-trigger), then dispatch to role(s). User-visible summary written
   to ledger questions/decisions.
7. Tests: trigger debounce; verdict validation (reject malformed); repeat-blocker
   escalation at exactly 2; change-request mapping on a fixture ledger ("make the
   bore fit a 25mm shaft" → bore dim + fit recalc + interference recheck, nothing
   else); mock provider (offline discipline — no all-skip).
8. MCP freshness + `graphify update .`.

DEVIATIONS / SEAMS (explicit, per advisor review):
1. TRIGGER CALL-SITE WIRING is partial by necessity. The subagent + the T-W5
   author's own NOTE at node_runner.py confirm the DAG path has NO run_id/ledger
   handle threaded through the context pack, and there is NO global provider
   registry in services/agent. So `_run_overseer_stage_exit` is a REAL call site
   but fires only when the context pack supplies `run_id` + `overseer_providers`
   (proven by a wired test); it no-ops otherwise so the DAG suite is not regressed.

   mission pipeline) and has no intent classifier — every `run_turn` is implicitly
   a change request, so there is no clean "user-message-classified-as-change-request"
   seam there. FULL run_id/ledger/provider threading through the pipeline is the
   remaining glue → recommend T-W19 (which already owns the pipeline glue), or a
   dedicated wiring task. Nothing in the running app auto-invokes the overseer until
   that glue lands; the capability is proven end-to-end via the in-app entry points.
2. REPLAN ROUTING split (§17): implemented ONLY the user change-request path here.
   Role-emitted `replan_request` routing (aicad.replan/1) is left to T-W19 per the
   assignment; `route_change_request` does not handle it.
3. ROUTING seam (§14): overseer→`strongest` via a hardcoded provider-preference
   list in `resolve_overseer_provider`, marked `TODO(T-W14)`. No role→model binding
   baked into logic — it is a seam that reads a provider map.
