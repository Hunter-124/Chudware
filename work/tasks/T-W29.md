## Context

Hunter directive 2026-07-05 (MAIN GOAL): "figure out the best way to tokenmaxx with the
local models, preferably run testing with diffusion gemma since you'll get much higher
TPS, unless you think it would be better to run normal gemma 4 e4b for parallelization."

Facts already established (T-W26): Gemma Diffusion is NOT llama.cpp-runnable (upstream
PR #24427 is a draft; non-autoregressive decode). The bundled runtime ships qwen3-4b
GGUF Q4_K_M primary + gemma3-4b-qat alt via pinned llama.cpp b9871. Hardware on this
machine: RTX 3080 Ti, 12 GB VRAM — a 4B diffusion model FITS on-GPU via a PyTorch/HF
transformers backend, so "higher TPS via parallel token decode" is testable NOW without
llama.cpp support.

The harness architecture spends tokens two different ways, and the answer may differ:
- SERIAL deep-think: ladder rungs, ponder delegations, council seat monologues —
  single-stream latency-bound → diffusion TPS advantage matters most here.
- PARALLEL fan-out: departments/workers, council seats concurrently, multi-doc part
  fan-out — aggregate throughput-bound → llama.cpp parallel slots (E4B/qwen3) may win
  on tokens/sec/GB and scheduling simplicity.

KEY RISK to measure, not assume: our worker roles depend on GBNF grammar-constrained
structured output (roles.py emits grammars). Diffusion decode has no llama.cpp grammar
path — measure schema adherence via prompted-JSON + validator retry rates instead, and
report whether the retry tax eats the TPS win.
